## 依頼文

```
リポジトリ Mitsuhira1/Web_app の PC ブラウザ版(web/pc-firebase/)で、
「<ゲーム名>」(ID: <ID>)のルール説明の動画を作り直してください。

マンカラ・大富豪の動画と、ほとんど同じ品質・同じ雰囲気の動画を作る。
- 実際のアプリの対局画面を録り、その上に注釈(説明の文・囲み・名札・番号・矢印・カーソル)を重ねる
- 1 本目は「何をするゲーム?」。ゲームを知らない人が、全部見たら遊べるようになるだけのステップを作る(数は増えてよい)
- 専門の言葉は、初めて出た所で説明する
- 分かりやすさ・見やすさを最優先する
手引きの 2 章「以前の動画の、だめだった所」は、ユーザーが実際に指摘したことです。一つも繰り返さないこと。
特に: 差す物が出る前に指さない/カットイン・盤の演出・結果の画面の間は注釈を出さない/
名札や文をほかの物(札・駒・穴・数の札・席・ボタン・ほかの名札)に絶対かぶせない/ゆっくり/
文と矢印を両方付けない/見れば分かることは文にしない。

■ 時間をかけて、品質を上げること(とても大事)
急いで仕上げないでください。時間がかかってかまいません(前の担当はマンカラ・大富豪それぞれに 1〜2 時間かけ、
「調べる → 設計 → 局面の手順を探す → 台本 → 1 本録る → コマで確かめる → 直す」を何度も繰り返しました)。
- 録る前に、ゲームの規則・盤の描き方・画面の空いている所を、よく調べて考えること

- 全部できたら、全部の動画をもう一度最初から見直し、「ユーザーが見て直しを求めそうな所」が無いか探して、あれば直すこと
- 「だいたいできた」で終わらせないこと。見本(マンカラ・大富豪)と並べて見劣りしないことが合格の目安です

■ 不具合を見つけたら
作業中に、アプリの不具合(規則・表示・カットインなどがおかしい所)や、今のルール文の誤りを見つけたら、
勝手に直したり、黙って避けたりせず、作業を止めてユーザーに伝え、直すかどうかを確認してから進めること。
(例: 大富豪では「革命」のカットインが出ない不具合が見つかり、ユーザーに確認してから直した。)
規則そのもの(core)は変えないこと。

  js/rules-steps.js を作り直す(直接は直さない)。tools/build_rule_steps.cjs の REMADE に ID を足す。sw.js の CACHE 名を変える
- 記録: README4AI_Claude_Codex_Antigravity.md の 5 章の先頭、docs/CHECKLIST_PENDING.md の先頭、
  docs/RULE_VIDEO_GUIDE_FOR_AI.md の 10 章の表
```
